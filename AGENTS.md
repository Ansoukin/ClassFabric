## Build Commands
- Desktop app: `dotnet build ClassFabric.Desktop/ClassFabric.Desktop.csproj -c Debug`
- Single library: `dotnet build ClassFabric.Core/ClassFabric.Core.csproj`
- Use NUKE only for release/publish builds, not verification.
- Release packaging: `./build.ps1 PublishApp` (Windows) or `./build.sh PublishApp` (Unix) with required metadata.
- `PublishApp` requires metadata: `--OsName windows|linux|macos`, `--Arch x64|x86|arm64`, `--Package folder|deb|pkg`, `--BuildType full|selfContained`, `--BuildName appBase|app`, `--AppVersion <version>`.
- Launcher packaging: `PublishLauncher` (native AOT self-contained).
- Plugin dev environment target `InitPluginDevEnv` writes user environment variables/profile blocks pointing at `out/ClassFabric_Dev`; do not run it casually during verification.
- **Stabilized invocation (use this on this machine)**: this build environment has recurring transient tool crashes (MSB6006 from csc/protoc, and the SimpleGitInfoGenerator source generator intermittently emitting an empty git tag → CS7034). Run builds with shared compilation and MSBuild node reuse disabled:
  ```powershell
  $env:MSBUILDDISABLENODEREUSE="1"
  dotnet build <project> -c <Config> -p:UseSharedCompilation=false
  ```
  If a weird tool crash still appears: `dotnet build-server shutdown`, kill lingering `msbuild`/`VBCSCompiler` processes, then retry. Do not "fix" such failures by editing code.

## Build Artifacts & File Cleanup

**Background**: File deletions executed in sandboxes (and some command-line contexts) get redirected to the Recycle Bin and pile up repeatedly; the user's C drive space is limited; build/download caches must live under E:\Project\NetYES.

**Rules (for build verification, especially AI sandbox execution):**
1. Build outputs must stay inside the repo's `bin/`, `obj/` (already git-ignored); never scatter them onto the system drive.
2. When cleaning outputs, prefer controlled bulk commands over per-file/per-directory deletion:
   - `dotnet clean` (recommended)
   - Or precise-path cleanup: `Remove-Item -Recurse -Force <explicit in-project path>`, limited to `bin/`/`obj/` only.
   - Never do untargeted full-disk scans followed by bulk deletion.
3. Never repeatedly create/delete temporary files in system locations: files under `AppData`/`LOCALAPPDATA` (e.g. `C:\Users\Windows\AppData\Local\AvaloniaUI\BuildServices`) must not be deleted by AI sandboxes (triggers Recycle Bin redirection); if cleanup is truly needed, leave it to the user or ask first.
4. Local temp/log files (`*.log`, `powershell.log`, etc.) never enter version control; handle them via `.gitignore`, not manual deletion.
5. `RoadMap.md` and `SPEC.md` are local private documents, **never commit** (see `.gitignore`); nobody may `git add` or commit them.
6. If large numbers of known files must be deleted (e.g. re-fetching assets, rebuilding caches), first tell the user which paths will be deleted, get confirmation, then run one single batch command, and state where everything ended up.

## Task Dispatcher & External Worker Workflow

Role split that prevents overreach:
- Project Owner: sets direction, approves tasks, accepts/rejects deliverables.
- Deputy Manager (repo assistant): prepares structured task briefs, dispatches ONE approved task at a time, personally verifies each deliverable (compile + diff) before reporting done, maintains SPEC.
- External worker agents: execute exactly one approved brief, never overstep scope.

External workers' required reading order: `AGENTS.md` → their task brief/spec guide → initialize `tm.md`. After any context compression, recover from `tm.md` first.

Hard rules (applied to every brief, report, and commit):
- No emoji in any communication, code, or commit.
- Task IDs MUST come from SPEC (e.g. `P1-0008`); never invent new IDs or codes.
- All task briefs and completion reports are delivered as Markdown code blocks / plain text.
- A brief must pin: exact file paths, precise edits, what NOT to touch, and concrete acceptance criteria.
- One task per dispatch; no batching or parallel branches on open tasks.
- The Deputy Manager independently re-verifies a worker's result (compile + `git diff`) before marking a SPEC item done.

## Worker Scratch Memory (tm.md)

**Background**: External workers (e.g. GLM) have limited context; long tasks that trigger context compression cause them to forget what was done, what remains, and how to do it. `tm.md` in the repo root is an external working memory that survives compression, preventing "compression amnesia". The old concept `tmemory` is deprecated and must not be used.

**Rules (mandatory for all external workers):**
1. First thing after taking a task: initialize `tm.md` from its built-in template — fill in the task ID and spec file version, and copy the full step list verbatim from the spec file.
2. After finishing each step: update `tm.md` immediately — tick the item and leave one line of evidence (build conclusion / changed file paths).
3. Before every reply to the user: refresh the three "current status" lines in `tm.md` (doing now / next action / blockers & pending answers).
4. First action after context compression or session restart: read `tm.md` + the spec file to restore context; never continue from residual memory.
5. `tm.md` uses a fixed template, full overwrite, no history appends; trim it yourself when it exceeds 120 lines.
6. `tm.md` is a memory scratchpad, not a completion report; official reporting still follows the report format in the task spec file.
7. After a task is accepted by the deputy manager, the deputy manager resets `tm.md` back to template state.
8. `tm.md` is a local private file, never commit (see `.gitignore`).

## Writing Style
- Commit messages and code comments must read naturally, like a human wrote them; avoid AI-sounding phrasing (e.g. over-templated leads, excessive buzzwords, unnatural politeness or hedging). Write commit `feat`/`fix` subject lines plainly and comments that state intent, not filler.

### Code Comment Hygiene
**Why this problem appears**: external workers are trained to follow specs strictly, so they tend to quote the spec inside code comments — citing ruling numbers ("per Q2"), spec files/sections ("see GLM_Guide.md §2.4"), task IDs, or dispatch-brief wording — as proof of compliance. This is wrong: a code comment is read by future maintainers who have never seen any spec, ruling, or task; process citations are noise to them.

**How to solve it:**
1. Code comments MUST NOT reference task IDs, ruling numbers, spec/guide files or sections, dispatch briefs, or any other process artifact.
2. A comment must stand alone: state the technical intent, constraint, or workaround itself. Self-test — would this sentence still make sense to a maintainer six months from now who never read the spec? If not, rewrite it to carry the technical meaning, or delete it.
3. Traceability (which ruling required a change, which brief requested a feature) belongs in the completion report and `tm.md`, never in code.
4. Example — bad: `// Collapse content root (per Q2 ruling)`; good: `// Collapse the whole root so the tinted capsule hides together with the content`.
